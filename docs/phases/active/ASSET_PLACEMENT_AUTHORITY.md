# Asset placement authority

## Invariants

- **INV-ASSET-LOC-001:** an installable asset requires a registered placement in the same tenant and branch; free text is never placement authority.
- **INV-ASSET-LOC-002:** an empty branch blocks creation and exposes creation flows for MDF, IDF or Warehouse while preserving non-sensitive return context.
- **INV-ASSET-LOC-003:** clients submit identifiers only. The backend resolves placement type, code, name, status, tenant and branch.
- **INV-ASSET-NOM-009:** placement is validated before a scoped, row-locked and rollback-safe nomenclature sequence is reserved.

## Audit and selected model

`branches` already represents the selectable authenticated branch context. `locations` is
the existing generic entity referenced by `assets.location_id`, but previously
had no type, canonical code or status. MDF/IDF are managed assets in `mdf_idf`;
there is no Warehouse entity. Racks alone have a partial MDF/IDF FK; Switch,
Patch Panel and PDU have optional rack FKs, while current specialized wizards
mostly collect location as discarded free text.

The lowest-risk model evolves `locations` into the common placement authority:
typed `MDF|IDF|WAREHOUSE`, canonical `placement_code`, active state and optional
container `asset_id`. MDF/IDF creation produces its placement in the same
request transaction. Warehouse is a placement row without an asset. Existing
untyped rows remain legacy and are not inferred or exposed as valid placement.

## Classification

MDF, IDF and Warehouse are placement containers and do not require a parent.
SWITCH, RACK, PATCH_PANEL, UPS, PDU and NODE are installable in this phase.
SERVER, FIREWALL, CCTV and AC_UNIT lack specialized persisted workflows;
BACKBONE represents endpoints rather than a single installation placement and
is deferred.

## Nomenclature and counters

Rules can opt into `include_placement`. The value is always the resolved
`placement_code`, never a literal custom segment. `nomenclature_counters` owns
the sequence per `(nomenclature, tenant, branch, placement)`. Reservation uses
an inserted counter row plus `SELECT FOR UPDATE`; transaction rollback restores
the counter. `MAX()+1` is prohibited. Existing assets and codes are unchanged.

For MDF/IDF, the complete managed `internal_code` is initially the canonical
placement code; no substring is inferred. Warehouse codes are generated by the
backend. A shorter explicit alias can be introduced later without rewriting
historical identities.

## Transaction, warehouse and security

Branch authority has one canonical chain:

`user → active user_branches in active tenant → POST /api/auth/select-branch → sessions.branch_id → RequireTenantTx → SET LOCAL app.branch_id → placements → counter(branch, placement) → asset`.

`GET /api/auth/select-branch` lists only active branches mapped to the current
user and tenant. The selector never supplies `branch_id` as authority to a DCIM
handler. It first changes the canonical session context, then protected requests
open a new `TenantTx` from that session. Therefore `TenantIdentityFromContext`,
the RLS GUC, placement resolution, counter scope and `assets.branch_id` use the
same value. A sole authorized branch is preselected; with multiple branches the
selection is explicit. Changing it clears placement and preview before reload.

`RequireTenantTx → resolve branch/placement → lock scoped counter → insert
assets → insert satellite → middleware commit`. Any error rolls back all work.
Warehouse placement forces the initial operational status to `inactive`; a
separate placement lifecycle (`installed/warehouse/transit/retired`) remains
future work.

Locations and counters use RLS/FORCE RLS. Runtime grants are the exact operations
needed by resolution, container creation and counter reservation. Cross-tenant
and cross-branch identifiers are invisible and rejected.

The final runtime allow-list is `locations: SELECT, INSERT, UPDATE` and
`nomenclature_counters: SELECT, INSERT, UPDATE`. `locations.UPDATE` is retained
only for the existing location-catalog PUT operation, now explicitly protected
by `RequireTenantTx`; no placement flow receives DELETE or DDL authority.

## Roundtrip and legacy

The shared selector retains only `return_to`, asset type and branch identifier,
reloads placements on focus, and clears placement when branch changes. Legacy
assets are not renamed or assigned a placement without evidence; they remain
`legacy_unresolved_placement` remediation debt. Rack-internal hierarchy and
more specific placement compatibility are future phases.
